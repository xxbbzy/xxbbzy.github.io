## 问题

Docker Compose 里写 `latest` 或者只写大版本号，初次部署没问题，时间一长就埋下两个坑：

- 换一台机器重新 `pull`，拉到的可能已经是另一个构建，行为未必和线上一致。
- 出问题想回滚，才发现当初跑的到底是哪个构建已经说不清了。

备份也一样：只备份数据卷里的文件，不备份 Compose 文件、环境变量文件和配置，重建时拼不回原来的样子，等于没备全。

## 做法一：标签全部锁到具体版本

逐个服务核对镜像仓库里真实存在的标签，写进 Compose 文件。2026-09-28 核对过的一批 homelab 服务，锁定的版本如下：

| 服务 | 锁定版本 |
| --- | --- |
| Jenkins | `2.568.3-lts-jdk21` |
| Nexus | `3.95.1` |
| Redmine | `6.1.3` |
| PostgreSQL | `16.14` |
| CoreDNS | `1.14.7` |
| Traefik | `v3.7.12` |
| step-ca | `0.30.2` |
| Prometheus | `v3.13.2` |
| Grafana | `13.1.3` |

写之前先确认标签在镜像仓库里确实存在，不要凭印象拼版本号；升级时只改这一个地方，改完记录下来，下次重建拉到的就是同一版本。

## 做法二：没有版本标签的，用 digest 锁定

不是所有镜像都提供版本标签。例如 `cturra/ntp` 只提供 `latest`，标签锁定这条路走不通，只能用 digest 锁定：

```yaml
image: cturra/ntp@sha256:<digest>
```

`digest` 是镜像内容的哈希，拉到的永远是同一个构建。写法上可以在旁边用注释记下当时的 `latest` 对应关系，方便日后看懂。

即使有版本标签，digest 也更彻底：同一个标签事后可能被重新构建推送。核对时就遇到过 `redmine:6.1.3` 的 digest 是较旧的构建、仓库里后来又重建了同一标签的情况。标签锁定解决“大概是哪个版本”，digest 锁定解决“精确是哪一次构建”。按需选用，不必所有服务都上 digest。

## 做法三：备份要备全，用增量快照

备份范围包括四类，缺一不可：

1. Compose 文件。
2. 环境变量文件（`.env`）。
3. 各服务的配置文件。
4. 绑定挂载（bind mount）的数据目录。

镜像本身不需要备份：标签或 digest 锁好了，重新 `pull` 就能拿回同样的镜像。

用 `rsync --link-dest` 做增量快照：每次备份生成一个完整目录，未变化的文件用硬链接指向上一次快照，磁盘占用只算新增和变化的部分，看起来是全量、用起来是增量。示意（路径用占位符，替换成实际路径）：

```bash
rsync -a --delete --link-dest=<上一次快照目录> <源目录>/ <本次快照目录>/
```

备份任务交给 systemd 定时器自动跑，保留期 2–4 周，过期快照按时间顺序删除。备份目的地放在独立的存储上（例如 NAS 上的 NFS 共享），不要和源数据放在同一块盘上。

## 注意事项

- 环境变量文件里常有密码和密钥：备份目的地本身也要控制好访问权限，备份内容绝不要放进公开仓库或公开文章里。
- 锁定版本不等于永远不升级：升级时一次只动一个服务，改标签或 digest，跑起来验证没问题再动下一个；升级记录和锁定版本放在一起，方便回滚。
- 备份做完不等于能恢复：建议定期抽一个快照，在隔离环境里按备份内容重建一次，确认 Compose 文件、环境变量文件和数据都在、服务能起来。没演练过的备份，只能算“希望它能恢复”。
